# v1.2 批跑归因报告 · 终版（2026-10-26，含两次自我纠错的完整档案）

> v1.2 首跑 75 题 avg 1.99/通过 18，结论类 57 题统一"漏提交"假死。用户令：查到真正原因。本报告=终版定案；中间两次被反转的结论如实保留在 §四（比结论本身更值钱）。

## 一、终版根因（一层 env 漏传 → 三连环）

**点火批跑时启动命令只传了 `PRISM_TRAJECTORY_FILE`，漏抄 `PRISM_API_BASE=http://127.0.0.1:8003`**（prism.py eval start 打印的标准命令两者都有——工具链无锅，纯手抄漏）。runner 的 API 缺省=8002 生产栈（runner.mjs:32），且 pi_gateway 池按 token 身份键控='eval'——于是整场批跑走了**生产栈**：

```
批跑75题 → 生产8002 → 生产网关9200 → 生产pi池(key='eval')
```

| # | 连环后果 | 证据 |
|---|---|---|
| ① | **数据面=生产库**（含 10-20 补导的 9 月末数据）——快照栈闲置未用 | 生产 gateway.log 83 次 `started pi rpc for eval`；sales-03 读到生产库真实的 E5 九月 3355（快照无此数） |
| ② | **轨迹写入生产回退文件** .pi/sessions/trajectories.jsonl（生产 pi 无 TRAJ env→extension 回退路径）；runner 读 eval 旧文件→按 userId 匹配不到→**"取最后一行"兜底→全批读同一条 14:35 冒烟期陈旧 fail 行**→57 题统一"漏提交" | 回退文件 95 行 15-17 点=批跑全程；eval 旧文件 162 行无一批跑行；报告 verdict 与陈旧行同源 |
| ③ | **extension 真实判定 ~87+/95 pass（与 v1.1 持平）**——1.99 分是判分数据源错位，不是 agent 退化 | 回退文件 verdict 分布 pass 101/fail 8（含历史行） |
| ④ | 附带：北极星生产轨迹被混入 95 行评估流量（已清理）；langfuse trace 落生产标签；eval 快照漂移闸通过（配置一致）但**管不住流量目的地** |  |

**"快照闸防住了配置漂移，没防住跑错栈"**——闸校验的是声明（stamp vs 题库），不校验流量实际落点。

## 二、为什么挖了七层才到（归因方法论档案）

排除掉的假设（每个都有实证）：服务令牌 401（/verify/claim 521 次全 200）→ 快照泄漏给 eval 栈（8003 实测返回快照数据）→ settled ②保底过严（git blame 证 10-13 未动）→ 台账写入断（73/75 会话有条目）→ JSON 截断致抽取失败（实测能抽出）→ 保底①本轮作用域乒乓（F1 真实存在的潜在 bug，但在本案非主因）→ **最终：env 漏传+错栈**。

关键破案线索：①"3355 与生产库精确相同不可能巧合"——这个疑点本身是对的，错的是我对"agent 在哪个栈"的前提；②轨迹文件日期分布（回退文件 15-17 点 95 行 vs eval 文件停在冒烟）一锤定音。

## 三、两次被反转的中间结论（如实保留）

1. **"sales-03 纯编造"（已反转）**：曾用词边界全库检索证明 3355 不在模型可见输入=编造——该论证在"agent 在 eval 快照栈"前提下成立；实际 agent 在生产栈，读到了真实的 9 月数据。**教训：证据链的有效性依赖前提，前提错了铁证也会指错方向。**
2. **"保底①乒乓是 57 题全灭主因"（降级为次要）**：F1（turnVerified 本轮→本链）仍是正确修复（真实潜在 bug：重试轮"一句话确认"会被误判漏提交），保留；但本案全灭的真因是②的陈旧行。
