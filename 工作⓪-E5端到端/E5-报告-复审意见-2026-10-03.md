## 一、P0 · 销量节的错误（比"半月合并"更严重）

### 1.1 事实澄清：不存在"半月销量"

`sales_trim` 的 `month` 字段是 **"X月中" / "X月末"**，语义是：

- **`X月中` 行 = 月中价格快照**，`retail` **全为 NULL**
- **`X月末` 行 = 整月销量快照**，`retail` 有值

实测：银河E5 共 286 行 = 143 个"月中"行（retail 全空）+ 143 个"月末"行（retail 有值）。

**所以"半月片"不是"半月销量"，报告中"半月片合并到月"这一步是在给一个本来就没有值的行做加法。** 正确口径只有一句：**取 `month LIKE '%月末'`，按 (year, month) 分组求和。**

### 1.2 更严重：整条 2026 序列实际是 2025 年的数

报告实际是"按 month 丢年分组"得到的，导致年份整体错位：

| 报告写 | 库里真实归属 | 数值 |
|---|---|---|
| 2026-01: 5882 | **2025-01 月末** | 5882 |
| 2026-02: 6955 | **2025-02 月末** | 6955 |
| 2026-03: 8727 | **2025-03 月末** | 8727 |
| 2026-04: 6864 | **2025-04 月末** | 6864 |
| 2026-05: 8495 | **2025-05 月末** | 8495 |
| 2026-06: 11004 | **2025-06 月末** | 11004 |
| 2026-07: 10179 | **2025-07 月末** | 10179 |
| **2026-08: 10774** | **2025-08 月末** | 10774 |
| 2026-09: 10377 | **2025-09 月末** | 10377 |

**用户说的"2026年8月只有 4452"是对的**——实测 **2026-08 月末合计 = 4436**（与 4452 差 16，疑为取整/口径差异，量级一致）。报告写 10774，**错了整整一年**。

### 1.3 真实月度零售序列（`month LIKE '%月末'`，按 year+month）

**2025 年**：5882 / 6955 / 8727 / 6864 / 8495 / 11004 / 10179 / 10774 / 10377 / 8988 / 7587 / 8328

**2026 年**：3028 / 1823 / 6508 / 5950 / 5203 / 7218 / 5162 / 4436 /（**9月月末行尚不存在**）

- 同口径 1–8 月同比：(68880 − 39328) / 68880 = **−42.9%**（报告写"约 −39%"，方向对、数错）
- 报告写的"2026-09: 10377"是 2025-09 的数；2026-09 库里**只有 9月中 行、没有月末行**，该月销量尚未结算。

### 1.4 返工口径

```
筛选 sales_trim 中 series='银河E5' AND month LIKE '%月末'
GROUP BY year, 月号   →  sum(retail) 即为该年该月整月零售
```

## 二、P1 · 终端价趋势混了版型/年款

报告："终端价趋势（sales_series_weighted tp）：2025-01 ¥128,875 → 2026-08 ¥96,531（降幅 25%）"

**问题**：`sales_series_weighted` 每月只有一行，是**全部版型的加权平均**。该表连"年款"字段都没有（`model` 恒为 `银河E5 EV`），msrp 同期也从 128,875 降到 116,567——**降幅里混着"版型结构变化"，不是真实降价**：

- 2025-08 走量：24款 530 探索+版，tp 111,370，mix 22%
- 2026-08 走量：26款 530 探索版，tp 99,940，mix 46%（24款已停产）

**同版型比较**（唯一有意义的比法）：26款 530Km 探索版，2025-08末 tp **113,620** → 2026-08末 tp **99,940**，真实降幅约 **12%**，而非报告宣称的 25%。

控制年款必须回 `sales_trim.model_name`（weighted 表做不到）。

## 三、P1 · 舒适性结论：三处硬伤

### 3.1 市场侧推不出"舒适性是结构性短板"

这部分**违反红线 #1 与项目刚定的分层规则**（[提纲 L27](../设计图总览/Prism-Agent-项目提纲.md)：

> "禁止某维没查完就用别的维度下结论"）。

销量下滑/终端降价的原因可以是：竞品增多、价格战、产品老化、渠道、补贴退坡……**用"结果下滑"反推"某个产品力维度差"是相关性当因果**。用户说得对：市场侧无法支撑该结论，真实用户反馈要去**舆情**找。

### 3.2 配置侧用最低配代表车系（且时间错配）

报告拿 **79311** 一个版型代表整个车系，得出"侧窗隔音玻璃缺失 → 产品力短板"。实测：

| 配置项 | 79311 | 79312/79266/79313/78132 |
|---|---|---|
| 侧窗多层隔音玻璃 | **-**（无） | **前排**（有） |

**"E5 无隔音玻璃"只对最低配成立**，不能当车系短板。且 79311 是 **2027款**（见第四节），拿它解释 2026 年的口碑/销量，时间上对不上。

### 3.3 口碑侧结论需限定范围

口碑只能说"**舒适是被吐槽最集中的维度之一**"，不能说"市场侧印证"。且 `其他` 桶 276 条（con 82.6%）未拆解前，"舒适最大短板"不稳（桶里很可能有噪声/异味/装配等舒适类抱怨）。

### 3.4 返工口径

- **口碑侧**：只下"口碑内"的结论（舒适 337 con / 续航 203 con 是吐槽最集中的两个维度）
- **配置侧**：只陈述事实 + 注明"**仅代表最低配 79311**"
- **市场侧**：**删除"印证"**，降级为"待回查项"
- **补数据缺口声明**：明确"舆情（外挂第四组）未接入，市场侧归因本轮不成立"

## 四、P0 · 配置节张冠李戴

报告："代表版本：79311（**530km 远航版**）"。实测 `config_snapshots` 中 79311 的车型名称是：

> **银河E5 2027款 550 智充启航版**

其余引用值核对：座椅材质=仿皮 ✓（全版型一致）、CLTC=550 ✓、前轮胎=225/55 R18 ✓、车机芯片=龍鹰6E ✓（均对 79311 成立）。

## 五、P2 · 其余瑕疵

### 5.1 口碑数字：未编造（重要，直接回答质疑）

逐格核对结果——报告二节表格**9 个维度的总数/pro/con 与 DB 完全一致**（合计 3235），口碑 1274 一致。3 条原文样本经查**真实存在**：

| review_id | sentiment | source_text |
|---|---|---|
| k_5789427 | con | 颠簸 |
| k_5833866 | con | 隔音有点差点意思 |
| k_5833242 | con | 稍微会有一些胎噪存在 |

**唯一瑕疵**：报告称"舒适 con 占比是 9 维度中最高"——不成立，`其他` 82.6% > 舒适 69.2%（应表述为"8 个命名维度中最高"）。

### 5.2 "retail 50% 缺失"是错误表述

不是数据缺失，是 **143 个"月中价格行"本就没有销量字段**（结构如此）。把它当"缺失"，会误导后续的人去修一个不用修的地方。应改为："销量只在月末行，月中行为价格快照。"

### 5.3 证据不是行 ID

报告写 `sales_trim:银河E5/*/*`、`config_snapshots:7650/.../79311`——**通配符不是行 ID，同事无法复算**，不满足 [任务清单 D1 验收标准](../设计图总览/Prism-Agent-任务清单.md)（"每个数字带数据源行 ID，能复算"）。需补 rowid 或可复算 SQL。

### 5.4 as_of 未逐维标注；口径未声明零售/批发

- 报告只有一个 as_of；配置（2026-10-01 快照）、销量、口碑时点不同，应逐维标注
- 全程用 `retail`（零售），未说明为何不用批发量——PM 看销量通常两者都看
