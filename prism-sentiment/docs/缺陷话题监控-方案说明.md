# 缺陷话题监控 · 方案说明（人读版）

> 2026-09-22 立项。官方 spec 在 `openspec/changes/defect-theme-monitoring/`（proposal / design / tasks / specs 四件套，commit 2a26e2a）。本文是给用户过目的方案摘要与决策确认单。

## 一、要解决的问题（你的原话）

> 「风云T7 仪表盘车道线消失，不少人在说，很可能引起舆情」

这类事的规律：**早期散落在中低互动帖的评论区**——发帖人可能只是个 50 赞的小博主，但评论区里几十人在抱怨同一个缺陷。等它爬上热帖榜被系统看到时，往往已经在出圈的路上。

现有系统为什么抓不到（双模式终审时确认的两个缺口）：

1. **看不全**：comment_theme 提点只读互动 top30 帖的评论。缺陷讨论早期恰恰在中低互动帖 → LLM 根本看不到。
2. **看不懂发酵**：状态机只看单点声量涨跌，「3 帖 → 30 帖的升温过程」没有专门盯防。

## 二、方案一句话

**把近 7 天的全量评论（不再只看热帖）拿来做关键词聚类，聚出的话题簇交给 LLM 判一次「是不是缺陷、叫什么名、多严重」，是缺陷的就作为「缺陷话题点」进点报页，后续发酵复用现有状态机。**

## 三、管线四步（全在 point_miner.py 内，约 +150 行）

```
近7天全量评论（口径同素材层：相关帖+自提及+真实作者）
        │
        ▼
① 评论池 _complaint_pool
   每条评论带：所属帖、内容、点赞、挂帖情感
   上限 5000 条（防极端日爆内存）
        │
        ▼
② 规则聚类 _cluster_complaints          ← 零 LLM 成本
   jieba 切词 → 去停用词 → 同一评论内词两两共现 → 连通分量切簇
   簇门槛：≥8 条评论 且 跨 ≥2 帖（孤帖高赞不算"话题"）
   打分：评论数 × (0.5 + 负面占比)，取 top5
        │
        ▼
③ LLM 簇判定 _judge_defect_clusters     ← 每车每日仅 1 次调用
   一次带上 ≤5 个簇（关键词 + 每簇 3 条代表评论）
   LLM 回答：是否缺陷 / 话题命名 / 严重度(high|mid|low) / 建议动作
   不是缺陷（闲聊簇）→ 丢弃
        │
        ▼
④ 合流进点报
   生成 origin=defect_theme 的防守点，七键同构进 _merge_points
   同一缺陷若已被 comment_theme 捞到 → 证据重叠自动归并成一个点
   后续发酵：复用状态机 new→active（active 即"🔥发酵中"）
```

**两段式的理由**：全量评论直接喂 LLM 会超窗又烧钱；规则聚类保覆盖（全量都过一遍），LLM 只做最后的质量把关（命名+甄别）。这是双模式「方案 3 混合管线」的同构延伸，不是新架构。

## 四、你在点报页会看到什么

- 筛选 chips：全部 / 宣传 / 防守 / **🔴 缺陷**（新增，缺陷话题专项视图）
- 缺陷点卡片示例：
  - 标题：**缺陷「仪表盘车道线消失」：47 条讨论**
  - 严重度 high 的标题带 ⚠ 前缀
  - 点开有：簇内代表评论 top3、涉及帖数、负面占比、LLM 建议动作
- 升温时该点自动转 active（🔥发酵中）——不另做预警横幅，语义已够用

## 五、⚠ 需要你确认的四个参数（我代拍的）

| # | 参数 | 我拍的值 | 备选与代价 |
|---|------|---------|-----------|
| 1 | 簇准入门槛 | ≥8 条评论 且 ≥2 帖 | 门槛低了误簇多（闲聊也成簇）；高了漏早期信号。8/2 是"至少有一小撮人在说"的经验线 |
| 2 | LLM 判定簇数 K | top 5 | 影响每车每日成本上限（1 次调用内装 5 簇）和信息量 |
| 3 | LLM 失败降级 | **静默不出缺陷点** | 备选是规则直出未命名簇——未命名的簇直接上页面是噪音，宁缺毋滥 |
| 4 | 「🔴 缺陷」chip 语义 | origin 专项视图；防守 chip 仍包含缺陷点 | 即：缺陷 ⊆ 防守，两层筛选不冲突 |

另有**簇负面度口径**顺带说明：评论本身没有情感字段，用「簇内评论来自负面帖的占比」做粗粒度信号——简单、现成、可测。

## 六、成本与风险

- **LLM 成本**：每车每日 +1 次 GLM-4-Flash 调用（装 ≤5 簇），相对现状增量可忽略
- **计算成本**：聚类是纯规则，单车日增 ~1k 评论级毫秒跑完
- **主要风险 = 误簇率**：闲聊簇混进 top5 浪费 LLM 判定、缺陷簇命名不准 → 实弹验收时人工核对（T4.1），这是本变更成败关键
- **LLM 把真缺陷误判为非缺陷（漏报）**：靠簇证据仍在池中、次日聚类再进 top5 自然重试缓解

## 七、测试与验收

- 单测覆盖：评论池口径（不相关帖/官方帖评论不进池）、簇准入边界（7 条不进 8 条进）、两簇不相连的连通分量正确性、LLM mock（混合判定/坏 JSON 静默降级）、合流归并
- 实弹：星愿现有数据跑一轮 regen，人工核对簇质量与误簇率；**风云T7 要等 TikHub 充值加车后才能实弹验证**（与本变更解耦，不阻塞开发）

## 八、不做的事（非目标）

- 跨车型缺陷关联（同一缺陷多车横向视图）——等真实需求
- 图片/视频类缺陷识别（OCR）——超出文本管线
- 独立预警推送——日级采集撑不起时效承诺
- 监控看板（PM 模式）新增组件——点报页（传播团队模式）承载

## 九、任务拆分（4 阶段 10 项，体量约 dual-mode 的 1/5）
