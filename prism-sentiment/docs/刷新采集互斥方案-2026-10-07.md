## 问题

用户点「刷新互动数」时 fleet 全车采集已在跑，刷新被 already_running 挡掉。但前端按钮没禁用，用户点了只弹弱提示，误以为刷新触发了全车采集。

根因：三个操作（单车采集 / 刷新互动数 / 全车采集）没有完整互斥，且全车采集状态不跨会话持久化。

## 4 个缺陷 + 修复方案

### D1：全车采集时刷新/采集按钮没禁用（P0）

**问题**：`index.html` 按钮禁用条件只有 `refreshing || loading`，没 `fleetCollecting`。

**修复（补反向禁用，P2-1）**：

```html
<!-- 采集按钮（index.html:47） -->
<button @click="triggerCollection"
        :disabled="!currentVehicleId || loading || refreshing || fleetCollecting" ...>

<!-- 刷新互动数按钮（index.html:53） -->
<button @click="triggerRefreshEngagement"
        :disabled="!currentVehicleId || refreshing || loading || fleetCollecting" ...>

<!-- 全车按钮（index.html:61）：反向——单车活动进行中时也禁用 -->
<button @click="triggerFleetCollect"
        :disabled="fleetCollecting || loading || refreshing" ...>
```

同时：`fleetCollecting` 时两个单车按钮 tooltip 补"全车采集进行中"。

> 说明：D1 的禁用依赖 `fleetCollecting`，而 `fleetCollecting` 的跨会话恢复由 D2 提供 → **D1 必须与 D2 一起实现才算完整互斥**，缺 D2 则刷新页面后禁用失效。

### D2：fleetCollecting 刷新页面丢失（P1）

**问题**：`fleetCollecting` 是前端内存，刷新页面清零，无法跨会话恢复禁用状态。

**修复**：后端新增 `GET /api/fleet/status`。

> **P1-1 导入**：`fleet.py` 现仅导入 `select`、`Vehicle`、`get_session`/`async_session`、`pipeline.frequency` 三函数。本端点新增以下导入（v1 漏列）：
> `from sqlalchemy import select, and_`、`from models.schemas import Vehicle, CollectionStatus`、`from api.pipeline_state import pipeline_phases`、`from datetime import date, datetime, timedelta`。

> **P1-2 脏锁容错（关键）**：判据必须与 `collection.py:169-173` 对齐——`is_running=True` 但 `lock_acquired_at` 超 30min 视为崩溃残留、不计入运行中。否则进程被 kill 后 DB 锁残留会让前端**永久**禁用刷新按钮。

```python
_LOCK_STALE_MINUTES = 30  # 与 collection.py 脏锁容错同值

@router.get("/status")
async def get_fleet_status(session: AsyncSession = Depends(get_session)):
    """全局采集活动状态：进行中车数 + 各车 phase。

    脏锁容错：is_running=True 但 lock_acquired_at 超 30min 视为崩溃残留，
    不计入运行中（对齐 collection.py:169-173），避免进程被 kill 后
    DB 锁残留导致前端永久禁用刷新按钮。
    """
    rows = (await session.execute(
        select(Vehicle, CollectionStatus).outerjoin(
            CollectionStatus, and_(
                CollectionStatus.vehicle_id == Vehicle.id,
                CollectionStatus.source == "all",
            )
        ).where(Vehicle.status == "active")
    )).all()

    now = datetime.now()
    in_progress = []
    for v, cs in rows:
        if not cs or not cs.is_running:
            continue
        lock_time = cs.lock_acquired_at or cs.last_collected_at
        if not lock_time or now - lock_time > timedelta(minutes=_LOCK_STALE_MINUTES):
            continue  # 脏锁，不计入
        phase = pipeline_phases.get(v.id, {}).get("phase", "unknown")
        in_progress.append({"id": v.id, "name": v.name, "phase": phase})

    return {
        "is_running": len(in_progress) > 0,
        "in_progress_count": len(in_progress),
        "vehicles": in_progress,
    }
```

**前端 `mounted()` 末尾恢复（P1-3 + P2-6）**：

```javascript
// mounted() 内追加：silent 拉取，失败不刷首屏 toast
async _restoreFleetState() {
    const st = await this.apiFetch("/api/fleet/status", { silent: true });
    if (!st || !st.is_running || !st.vehicles.length) return;
    this.fleetCollecting = true;
    // P1-3 关键：_pollFleet 首行是 Date.now() - fleetStartTime > 120min，
    // 而 fleetStartTime 初值 0 → 不设它会在首次轮询立刻判"超时"并复位。
    this.fleetStartTime = Date.now();
    this._startFleetPolling(st.vehicles.map(v => v.id));
}
```

> **P2-4 限制说明**：服务重启后 `pipeline_phases` 为空，`/status` 的 `phase` 会是 `"unknown"`（仅用于展示）。恢复轮询的"完成"判定走 `/pipeline-status`，不依赖此 `phase`。但注意 `/pipeline-status` 第 4 步回落（`collection.py:351-358`）在内存相位缺失时会返回 DB 上一轮的 `status`（可能仍是 `"completed"`）——若出现"恢复后立刻显示完成"，属该回落语义所致，后续可单独收敛（不在本方案范围）。

### D3：already_running 不区分单车/全车（P1）

**问题**：`already_running` 响应只带 `phase`，用户不知道是单车采集还是全车采集挡的。

**修复（P2-2 改为复用 D2，单一真相源）**：**不改 `collection.py` 的响应**，前端在 `already_running` 分支直接查 `GET /api/fleet/status` 判断（P2-3 阈值 `>= 2 台` 判 fleet）：

```javascript
if (data.status === "already_running") {
    this.pipelinePhase = data.phase;
    const st = await this.apiFetch("/api/fleet/status", { silent: true });
    if (st && st.in_progress_count >= 2) {
        // 多台并发 → 全车采集
        this.showToast(`全车采集进行中（${st.in_progress_count} 台），请等待完成后再刷新互动数`, "info");
    } else {
        const label = {collecting:"采集中", analyzing:"分析中", calculating:"计算中", refreshing:"刷新中"}[data.phase] || data.phase;
        this.showToast(`该车正在${label}，请等待完成后再刷新互动数`, "info");
    }
    this.refreshing = false;
    return;
}
```

> **删除 v1 的 `scope` / `fleet_in_progress` 后端改动**：v1 让 `trigger_refresh_engagement` 调 `_check_fleet_running(session)`（P1-4：该函数从未定义）并返回 `fleet_in_progress`（P1-5：布尔值被前端当台数渲染成"（true 台）"）。复用 `/status` 后，`collection.py` **无需改动**，也消除 D2/D3 两处同语义逻辑的漂移。

### D4：刷新排队缺失（P2，暂不做队列）

**问题**：全车采集期间被挡的刷新没有排队，用户只能反复点击。

**修复**：暂不做队列（复杂度高）。**只保证 D3 的提示文案清晰**（v1 曾写"提示预计 X 分钟后完成"，但 `/status` 无 ETA 数据源，该句不可落地，已删）。如后续要做 ETA，需先定义算法（如：剩余车数 × 单车耗时均值）并在 `/status` 增加 `eta_minutes` 字段。
