## 三、关键设计决策记录

| 决策 | 结论 | 理由 |
|------|------|------|
| 双模型分工 | Qwen3-4B：sentiment + dim_sentiment；GLM-4.7：is_event + event_tags + event_description + opinion_tags | 本地模型做结构化输出更稳定，API模型做复杂语义理解更灵活 |
| 过渡期 | Qwen3-4B 未就绪时，sentiment + dim_sentiment 由 GLM-4.7 兼任 | 保证流程不阻塞，微调完成后无缝替换 |
| 事件标签 | 预定义标签池，LLM 从池中选最多 3 个 | 可控可聚合，避免自由提取碎片化；见下方标签池定义 |
| opinion_tags | LLM 自由提取，不受标签池限制 | 观点标签是开放性的，需要灵活表达 |
| 事件描述 | 一个 event_description 覆盖所有事件 | 多事件天然关联，拆分反而碎片化 |
| 非事件帖子 | is_event=false，event_tags=[]，event_description="" | ~60-70% 帖子不是事件，不硬贴标签 |
| 评论分析方式 | 批处理总结（非逐条），一个帖子一次 LLM 调用 | Simon Willison 模式验证可行，省 token，天然抗噪音 |
| 评论分析范围 | 仅 Top 5 热门帖子的评论，半月窗口 | 成本可控，信息密度最高 |
| Top5 时间窗口 | 固定半月窗口（1-15日 / 16-月末），5天边界重叠 | 稳定可预期，月末最后5天计入下月前半段，月初前5天计入当月后半段 |
| 吵架/水军检测 | 批处理总结时标记 `is_argumentative`，提取 `genuine_themes` | 车型场景水军动机弱，LLM 总结时自然识别，不单独模块 |
| 热度排序公式 | `likes×1 + comments×5 + shares×10` | 转发价值 > 评论 > 点赞，参考 BettaFish |
| 帖子 vs 评论差异 | 看板展示帖子情感 vs 评论区 genuine_sentiment | 揭示"表面正面但评论区翻车"等关键洞察 |
| 内容去重 | SimHash 64位指纹，Hamming距离 ≤3 | 比 Jaccard 更适合短文本近似去重，O(n)比较 |
| 事件聚类 | DBSCAN 密度聚类（同 event_tag 内按时间） | 无需预设K，自动处理噪声点，7天半径 |
| 全文抓取策略 | Trafilatura 优先，Crawl4AI 兜底 | 纯Python库成功率80%+，无需浏览器；失败再上Playwright |
| 小红书URL解析 | xhslink.com 短链 → HTTP重定向 → 正则提取 note_id | 短链有 /a 和 /m 两种格式，必须先解析重定向 |
| 分组看板归一化 | 不归一化，标注各车型数据量级 | 保持原始数据透明，避免归一化失真 |
| DB 迁移策略 | 开发阶段重建数据库（`drop_all + create_all`） | 改动量大（6表改字段+3新表），迁移脚本成本高于重建 |
| 本地推理优化 | Qwen3-4B 可选 INT4 量化（吞吐翻倍） | RTX 4080 12GB，INT4 精度损失 <2% |
| 增量采集 | 只拉新帖，不全量重拉 | 减少重复采集压力，靠 SimHash 去重兜底；通过 published_at + platform + URL 判断是否已存在 |
| 图片内容 | 不纳入分析 scope | OCR/多模态成本高，车型舆情核心在文本，暂不投入 |
| 评论总结范围 | Top 5 帖子无论是否事件都做批处理总结 | 非事件热门帖子的评论区同样有产品洞察价值 |
| LLM JSON 稳定性 | 智谱 JSON mode + Pydantic 校验兜底 | 智谱 API 支持 `response_format: {"type": "json_object"}`，保证合法 JSON；Pydantic 做最终字段校验 |
| GLM 调用策略 | sentiment/dim_sentiment 用 GLM-4-Flash（免费），事件标注/评论总结先试 Flash 不够再升 Plus | GLM-4-Flash 免费（速率限制 ~16-100 RPM），日均调用量远低于限制；月成本预估 < ¥50 |
| API 重试 | `tenacity` 指数退避重试 | 网络抖动和速率限制的通用解法 |
| 时间衰减 | `score × 0.95^days`（每日衰减5%，约14天降到50%） | 可配置参数，后续实测调优 |

## 四、7 项改造详解

### 改造 1：新闻全文抓取（Trafilatura + Crawl4AI）

**痛点**：`news_collector.py` 只有 snippet ~100字 → `analyzer.py` 分析精度低

**方案**：新增 `full_text_crawler.py`，两级抓取策略
- **第一级**：Trafilatura（纯Python库，无需浏览器）
  - `trafilatura.fetch_url()` + `trafilatura.extract(favor_precision=True)`
  - 成功率 80%+，速度快，资源占用低
  - 全文 ≥200字才算成功
- **第二级**：Crawl4AI（Playwright 无头浏览器）兜底
  - 一个浏览器实例复用抓多条（`make_crawler()` 上下文管理器）
  - 仅当 Trafilatura 失败时调用
- **兜底**：两级都失败时 fallback 到 snippet 继续分析（不跳过）
- 结果存入 `RawPost.full_content`（新增列）

```python
import trafilatura
from crawl4ai import AsyncWebCrawler

async def crawl_full_text(url: str, snippet: str = "") -> dict:
    # 第一级：Trafilatura（快速、轻量）
    result = _try_trafilatura(url)
    if result["status"] == "success":
        return result
    # 第二级：Crawl4AI（重型、可靠）
    result = await _try_crawl4ai(url)
    if result["status"] == "success":
        return result
    # 兜底：用 snippet
    return {"url": url, "full_text": snippet, "status": "fallback"}

def _try_trafilatura(url: str) -> dict:
    try:
        downloaded = trafilatura.fetch_url(url)
        if not downloaded:
            return {"url": url, "full_text": None, "status": "failed"}
        full_text = trafilatura.extract(
            downloaded, include_comments=False,
            include_tables=True, favor_precision=True,
        )
        if full_text and len(full_text.strip()) > 200:
            return {"url": url, "full_text": full_text, "status": "success"}
        return {"url": url, "full_text": None, "status": "failed"}
    except Exception:
        return {"url": url, "full_text": None, "status": "failed"}
```

### 改造 3：内容去重 + 评论独立 + URL解析

**痛点**：
- `news_collector.py._dedup_key()` 只做 URL 级去重，同事件多源重复
- `media_crawler.py:148-149` 把评论拼进 content，污染分析
- 小红书短链无法直接匹配同一帖子的不同来源

**方案 A — 去重**：新增 `deduplicator.py`
- SimHash 64位指纹 → Hamming 距离 ≤3 → 标记同组
- 同组保留最早一条，其余标记 `duplicate_group_id`
- 依赖 `simhash` 库（pip install simhash）

```python
from simhash import Simhash

def deduplicate(posts: list[dict], threshold: int = 3) -> list[dict]:
    kept = []
    fingerprints = []
    for post in sorted(posts, key=lambda p: p.get("published_at", "")):
        text = f"{post.get('title', '')} {post.get('content', '')}"
        fp = Simhash(text)
        is_dup = False
        for kept_fp in fingerprints:
            if fp.distance(kept_fp) <= threshold:
                is_dup = True
                break
        if not is_dup:
            kept.append(post)
            fingerprints.append(fp)
    return kept
```

**增量采集策略**：只拉新帖，不全量重拉。通过 `published_at + platform + source_url` 判断帖子是否已存在：
```python
def _is_new_post(session, post: dict) -> bool:
    """检查帖子是否已存在，避免重复采集"""
    url = post.get("url") or post.get("source_url", "")
    if url:
        exists = session.query(RawPost.id).filter(
            RawPost.source_url == url,
            RawPost.vehicle_id == post["vehicle_id"]
        ).first()
        if exists:
            return False
    # 无 URL 的社交媒体帖用标题+时间窗口去重
    title = post.get("title", "")[:100]
    pub_date = post.get("published_at")
    if title and pub_date:
        exists = session.query(RawPost.id).filter(
            RawPost.title == title,
            RawPost.vehicle_id == post["vehicle_id"],
            RawPost.published_at.between(pub_date - timedelta(hours=1), pub_date + timedelta(hours=1))
        ).first()
        if exists:
            return False
    return True
```

**小红书短链解析**：`media_crawler.py` 返回的 URL 可能是 xhslink.com 短链，需先 HTTP 重定向解析再提取 note_id：
```python
import re, httpx

XHS_URL_PATTERNS = [
    re.compile(r'/explore/([a-f0-9]{24})'),
    re.compile(r'/discovery/item/([a-f0-9]{24})'),
    re.compile(r'/user/profile/\w+/([a-f0-9]{24})'),
    re.compile(r'/([a-f0-9]{24})(?:\?|#|$)'),
]

async def resolve_note_id(post_url: str) -> str | None:
    url = post_url.strip()
    if "xhslink.com" in url:
        url = await _resolve_short_link(url)
    for pattern in XHS_URL_PATTERNS:
        match = pattern.search(url)
        if match:
            return match.group(1)
    return url.rsplit("/", 1)[-1].split("?")[0].split("#")[0]

async def _resolve_short_link(short_url: str) -> str:
    try:
        async with httpx.AsyncClient(follow_redirects=True, timeout=5) as client:
            resp = await client.get(short_url)
            return str(resp.url)
    except Exception:
        return short_url
```

**评论分析（Top 5 帖子，批处理总结）**：

评论不做逐条情感分析，改为对每个热门帖子做一次批处理 LLM 调用，输出评论区的整体总结。**无论帖子是否为事件帖，只要进入 Top 5 就做评论总结**——非事件热门帖子的评论区同样有产品洞察价值。

**Top 5 选择时机 — 半月窗口**：
- 固定窗口：每月 1-15日为前半段，16日-月末为后半段
- 边界重叠规则：月末最后5天同时计入下月前半段；月初前5天同时计入当月后半段
- 在当前窗口内按热度分排序取 Top 5
- 热度分公式：`likes×1 + comments×5 + shares×10`

```python
from datetime import datetime, date

def get_current_period() -> tuple[date, date]:
    today = date.today()
    if today.day <= 15:
        start = today.replace(day=1)
        end = today.replace(day=15)
    else:
        start = today.replace(day=16)
        # 月末日期
        if today.month == 12:
            end = date(today.year + 1, 1, 1)
        else:
            end = date(today.year, today.month + 1, 1)
        end = date.fromordinal(end.toordinal() - 1)
    return start, end

def get_boundary_overlap_periods() -> list[tuple[date, date]]:
    """月末最后5天 → 计入下月前半段；月初前5天 → 计入当月后半段"""
    today = date.today()
    periods = [get_current_period()]
    # 月末最后5天也作为下月前半段候选
    if today.day >= 28 and today.month != 12:
        periods.append((date(today.year, today.month + 1, 1),
                        date(today.year, today.month + 1, 15)))
    # 月初前5天也作为当月后半段候选
    if today.day <= 5:
        mid = today.replace(day=16)
        if today.month == 12:
            end = date(today.year + 1, 1, 1)
        else:
            end = date(today.year, today.month + 1, 1)
        end = date.fromordinal(end.toordinal() - 1)
        periods.append((mid, end))
    return periods
```

- **参考验证**：Simon Willison 用 Claude 总结 HN 讨论（同类实践），LLM 做吵架识别已验证（arXiv 2512.03005）

### 改造 6：事件脉络追踪

**痛点**：事件标签是单帖子分类，没有跨帖子关联和时间线

**方案**：参考 TrendSonar `topic_service.py`
- 同 event_tag 内用 DBSCAN 密度聚类，按帖子时间戳自动分组
- 7天半径（eps），min_samples=1（单帖子也成组）
- 无需预设 K（相比 K-Means 更适合舆情场景，事件数量不可预知）
- 噪声点自动标记（label=-1），不会强行归入不合适的组
- event_description 用 Jaccard 相似度辅助判断是否为同一事件的不同报道
- LLM 为每组生成一句话摘要
- `dashboard.py` 新增事件时间线 API
- 帖子有多个 event_tag 时，会分别归入对应的 EventGroup

```python
from sklearn.cluster import DBSCAN
import numpy as np
from collections import defaultdict

def cluster_events(analyzed_posts: list[dict], time_window_days: int = 7,
                   eps: float = 0.3, min_samples: int = 1) -> list[dict]:
    tag_buckets = defaultdict(list)
    for post in analyzed_posts:
        if not post.get("is_event") or not post.get("event_tags"):
            continue
        for tag in post["event_tags"][:1]:
            tag_buckets[tag].append(post)

    groups = []
    group_id = 0
    for tag, posts in tag_buckets.items():
        if len(posts) == 1:
            groups.append(_make_group(group_id, tag, posts[0]))
            group_id += 1
            continue
        times = np.array([p["analyzed_at"].timestamp() for p in posts]).reshape(-1, 1)
        db = DBSCAN(eps=time_window_days * 86400, min_samples=min_samples, metric="euclidean")
        labels = db.fit_predict(times)
        for label in set(labels):
            if label == -1:
                # 噪声点各自成组
                for idx in np.where(labels == -1)[0]:
                    groups.append(_make_group(group_id, tag, posts[idx]))
                    group_id += 1
            else:
                members = [posts[i] for i in np.where(labels == label)[0]]
                g = {"id": group_id, "event_tag": tag,
                     "start_time": min(m["analyzed_at"] for m in members),
                     "end_time": max(m["analyzed_at"] for m in members),
                     "post_ids": [m["id"] for m in members],
                     "post_count": len(members),
                     "representative_desc": members[0].get("event_description", "")}
                groups.append(g)
                group_id += 1
    return groups
```

## 八、与微调项目的接口约定

微调项目（独立仓库）产出后，本项目通过以下接口对接：

```python
# pipeline/analysis/dim_sentiment_model.py（预留）
class DimSentimentModel:
    """本地微调 Qwen3-4B，输出 sentiment + 14维度情感"""

    DIMENSIONS = [
        "动力/加速", "续航里程", "电耗", "充电体验",
        "智能化/车机", "辅助驾驶/智驾", "价格/性价比", "舒适性",
        "操控", "安全性", "内饰", "外观", "空间", "售后服务"
    ]

    def predict(self, text: str) -> dict:
        """
        返回 {
            "sentiment": "positive/negative/neutral",
            "dim_sentiment": {"舒适性": -1, "动力/加速": 1, ...}
        }
        """
        raise NotImplementedError("微调模型尚未部署")

    def is_available(self) -> bool:
        return False
```

**约定**：
- 微调模型的输入输出格式：输入 `str`，输出 `{"sentiment": "...", "dim_sentiment": {...}}`
- 模型文件路径：`models/dim_sentiment_qwen3_4b/`（本项目内，gitignore）
- **过渡期**：`DimSentimentModel.is_available() == False` 时，sentiment + dim_sentiment 由 GLM-4.7 API 兼任
- **对接后**：`analyzer.py` 检测到本地模型可用，替换 GLM-4.7 的情感+维度调用，GLM-4.7 仍负责事件标注
- **本地推理性能**：Qwen3-4B 在 RTX 4080 12GB 上预估 ~30-40 tokens/s，一轮 200 帖子约 10-17 分钟；可选 INT4 量化提速
