## PM 性落点索引（2026-10-01 增补·让 agent 像汽车 PM 思考）

> PM 性是贯穿全栈的核心命题，不只和提纲有关。原则见提纲 §5.1.1，架构落点见运行架构.html harness 五层节点，本清单追踪执行任务。提示词管"怎么想"，工具门控管"流程纪律"，口径视图管"数字正确"，验证器管"结论可靠"，评估集管"持续校准"——五层合起来才是 PM 性，缺一就退化成"会聊车的 chatbi"。

| PM 性落点 | 对应任务项 | 所在阶段 | 验收要点 |
|---|---|---|---|
| ① 棱镜SOP流程骨架（提示词层） | D2.1.1 棱镜 SOP system prompt | 阶段2.1 | 三层推进纪律+结论定义+两层提示词；before_agent_start 动态注入 |
| ② 状态栏挂三维度完成度（上下文层） | D2.1.2 状态栏+agent外壳 | 阶段2.1 | agent 自见哪维没查=PM checklist 习惯 |
| ③ 三核心工具=棱镜物化+工具门控（工具层） | D2.2.3 TS语义工具直读库 | 阶段2.2 | 没查配置时销量工具不给（setActiveTools 阶段解锁） |
| ③ 口径视图=PM类型系统（工具层） | D2.2.2 口径视图 v1 | 阶段2.2 | 数字带口径元数据，agent 拿到非裸数字 |
| ④ 完成验证器=PM复核（验证层） | D2.3.2 完成验证器 | 阶段2.3 | 每结论带 evidence:[row_id]+as_of，独立验证器替 agent 复核 |
| ④ 口碑定性结论单独一套（验证层） | D2.3.3 口碑定性结论 | 阶段2.3 | claim 溯源+人工抽检（六分制对口碑失效） |
| 评估集=PM专业判断活资产 | D2.4.1 评估任务集 v1 | 阶段2.4 | **30-50 问题必须用户写**，trap tasks 是 PM 才会踩的坑 |
| golden case=PM 范本（few-shot） | D1.4 棱镜综合 + D1.5 报告 | 阶段1 | E5 端到端报告=PM 会怎么分析一台车的 in-context 范例 |
| 三维度并行=多源交叉（编排层） | D2.2.3 工具层 + 八项稿工作⑤ | 阶段2/5 | pi-subagents 三维度独立并行+结构化摘要回传 |

**关键纪律**：① 评估集问题 AI 写会偷工减料（教材实战："AI不会自己停下来"是 AI PM 核心价值），**必须用户写**；② golden case（银河E5）是 agent 学习 PM 思维的 few-shot 范本，不是普通测试数据；③ trap tasks 要瞄准"AI 易犯、PM 不会犯"的错（如用相邻车系数据补缺）。

> 原散在 v1 的 ④⑤⑦ 且被砍一半，云单机下必须前置成独立块。原 50-100 多实例+SLB 降级为远期扩展项（D3.11）。

- [ ] D3.1 会话状态可恢复（二选一）：① SessionManager.inMemory + Redis 外置共享；② 内存会话 + 定期落独立 SQLite 快照（pi 支持从 DB 条目恢复）。验收：pi 进程重启后会话不丢。

## 阶段 6：badcase 驱动迭代

**核心交付物 D6**：可验证可回滚的能力更新机制。
**验收**：badcase → 提案 → 四项发布门槛 → 灰度，全链路跑通。

- [ ] D6.1 badcase 归类归因——**先查评测系统，再查 agent**（分数下降先查验证器bug/数据源失效/用例脱节）。归因输出不只是分类，要落到"改哪层"——**归因枚举 × 修改路径映射表**：
  | 归因 | 改哪层 | 动作 |
  |---|---|---|
  | prompt 问题 | system prompt | 最小 diff（D6.2）|
  | tool schema 问题 | TS 语义工具 schema | schema 修订 + expected_* 更新 |
  | retrieval 数据旧 | 数据源 | as_of 检查 + 采集补（管理者授权）|
  | 权限 | PEDO/工具白名单 | 权限规则修订 |
  | 下游系统 | 供给端契约 | 找用户（供给端黑盒，Prism 不管内部）|
  | 模型限制 | model swap | 诊断分流（v4-flash vs v4-pro）|
  验收：每条 badcase 归因后能直接指到"改哪层 + 具体动作"，不是停在分类。
- [ ] D6.2 每周提案：DeepSeek 当 coding agent 对 system prompt 做最小 diff（只写 working.txt）→ 四项发布门槛 → 过则灰度（40人内部场景"灰度"=管理者自己先用，不上canary基础设施）。
- [ ] D6.3 保留集不退化才全量：保留集=已能正确给的结论；边界集=原本答错的边缘case。
- [ ] D6.4 分层评估：提案有效率/产物激活率/遵循成功率/保留集增益（Harness-updating ≠ Harness-benefit）。
- [ ] D6.5 tokenizer 回归门禁（挂对对象）：挂在舆情打标管线（Qwen3-4B 本地模型），**不挂主链路**（DeepSeek API tokenizer 在服务端）。
- [ ] D6.6 三维度并行：DeepSeek 2500 并发配额宽裕，复杂归因保留激进用法，简单查询走串行。留串行 fallback。
