## 一、地基级问题（必须先解决）

### 问题 1：部署形态三处互相矛盾，砍基建的依据不成立

**级别**：P0

**现状**：
- `文档/Prism-Agent-项目提纲.md` §4.3 决策 8（标注“不可推翻”）：云服务器，按 40 人峰值设计，**明确推翻“无服务器单机”旧约束**；§9 待定 #2 还写了“云服务器形态下倾向正式登录”。
- `设计图/Prism-Agent-八项工作设计稿.html` 总纲却把“单机 + 无服务器 + pi 部署在工位机不是云”写成**“范围约束（明确）”**，并以此为唯一理由砍掉 K8s/Vault/Prometheus/ELK/McNemar/canary。
- 同一份八项工作稿工作⑤的待拍板里又出现“部署形态：云/本地/混合？”——总纲说已明确，⑤还在待拍板，同稿内矛盾。

**为什么是地基级**：云服务器和工位机是两种完全不同的安全模型、可用性模型和成本模型。这个不拍板，砍基建清单、部署测试清单、认证方案全部会反复返工。

**建议动作**：
- 若维持提纲的云决策 → 砍基建理由需重写，部署测试清单需补认证测试（见问题 10）。
- 若真回到工位机 → 必须正式推翻提纲决策 8 并回写提纲 §4.3。
- 先拍板，再谈砍什么。

---

### 问题 2：工作⓪ 的销量、配置两维无落地数据，第一交付物会断链

**级别**：P0

**现状**：
- Atuohome 侧事实源 `C:\Users\<you>\Desktop\Agent项目\Atuohome_Agent\docs\口碑配置项目-autohome-agent改造方案-v1.md` 明确写着：autohome.db **“无配置表、无销量表”**，CAM 导入（fact_terminal）在 T13 排队。
- 而八项工作稿工作⓪ 的最小路径是“查销量（autohome.db 直读）→ 查口碑 → 查配置（车型配置表）”。

**三维具体断链**：
- **销量**：“从 series_summaries 或销量源取 E5 月度销量”——series_summaries 是之家摘要，即便有销量字段也是之家口径，与 CAM 正式口径对不上账，违背自己定的“口径一致”红线；“或销量源”含糊带过。
- **配置**：“从配置表取 E5 关键配置项”——库里没有配置表，配置数据躺在 `data/config_snapshots/*.json`（约 260 个 spec 的 JSON，未入库），E5 的 spec 快照是否在内未验证；且只取“轴距/功率/续航/智能座舱”四参数，已定稿的赋分体系（score_default/override、概念配置赋值表定稿 2026-09-26）完全没接，配置维度退化成参数罗列，“配置=产品力”的棱镜方法论丢失。
- **口碑**：6,196 条已打标里 E5 占多少未验证（工作③步骤 1 有自查，但工作⓪步骤里没有）。

**建议动作**：工作⓪ 开工第一步改为 **“E5 数据可得性盘点”**（三张表 + config_snapshots 实际行数清点），把销量/配置两维的取数路径写实。否则第一交付物会卡在数据上而非分析上——正是 v2 最想避免的“动不了手”。

## 二、两稿之间不同步

### 问题 3：施工顺序两套链，MCP 桥 P0 放错位置

**级别**：P1

**现状**：
- 八项工作稿 v2：`P0 MCP桥(gate) → ⓪E5端到端 → ①SOP → ②注册表…`
- `设计图/Prism-Agent-运行架构.html` 底部“建设顺序（已定调）”：`注册表 → 口径视图 → TS工具 → MCP桥验证(第④) → sentiment封装`——**整条链里没有工作⓪**，明显是 v2 之前的版本，但无任何“已被取代”标注。

**额外问题**：P0 放全链第一个 gate 逻辑不成立——工作⓪ 是纯 Python 脚本直读 SQLite，不经 pi、不经 MCP，P0 与第一交付物零依赖；提纲 §5.6 也已定调“验证推迟到口碑工具接线时”。

**建议动作**：P0 挪到“②TS 语义工具接线”之前；工作⓪ 立即开跑，不被 gate 阻塞；运行架构稿加“部分内容已被八项稿 v2 取代”标注或升 v0.2。

### 问题 6：北极星三处定义不一致，“零幻觉”不可计算

**级别**：P1

**现状**：
- 第 0 步（“已定调不再拍板”）：`PM拿到正确结论的比例 = Pass^1 × 零幻觉`
- 工作③：“北极星**修正为**单位成本正确率 = Pass^1 × 零幻觉 ÷ 单次成本”
- 工作⑧：“北极星 = 边界集通过率 + 保留集不退化 + 纠正率下降趋势”

三处三个式子，“已定调”和“修正后”并存。且提纲 §9 #8“成功指标”仍是待定状态——北极星拍了板却没回写事实源。

**额外问题**：
- `× 零幻觉` 作为乘数项无法落地：若“零幻觉”严格为 0，乘积恒为 0；若是比率应写成 `×(1−幻觉率)`。
- v4-flash 是 ¥1/M 价格，提纲自己说“成本便宜到可忽略”，单位成本做分母时波动几乎全由分子决定，北极星的区分度需再想。

**建议动作**：统一为一个公式并回写提纲 §9 #8；明确“零幻觉”的落地口径（是否 `1−幻觉率`）；重新评估“单位成本”作分母是否有区分度。

### 问题 7：调度方案推翻了已拍板的 D2

**级别**：P1

**现状**：
- 数据层方案 D2（已拍板）：“**不做定时日更**，staleness 门按需增量，理由是 40 人内部产品撑不起调度器复杂度”。
- 八项工作稿工作②步骤 6 却要“接 event-trigger 补调度：RecurringTimer **周期扫口碑** + FileWatch 监听销量落地”——这正是 D2 否决的主动调度模式。

**额外问题**：“允许触发采集需管理者授权”与 staleness 门“任何用户查询自动触发增量”的边界没切清——红线类设计不该带着“细则待定”进施工链。

**建议动作**：要推翻 D2 需给理由并回写数据层方案；不推翻就把这条改成 staleness 门实现；同时切清“管理者授权”与“自动增量”的边界。

## 四、事实性错误

### 问题 8：“包住两项目 17 项能力”张冠李戴

**级别**：P2

**现状**：
- “17 项”真实出处是 `文档/Prism-Agent-读书映射.md` §8“增量**工作**清单（两轮合计 17 项）”——是**工作项数量**，不是两项目能力数。
- 实际能力数：Atuohome 22 个 MCP 工具（提纲 §3/§5.6），MVP 桥接 15 个（数据层方案 8.1），舆情 14+2 端点（提纲 §5.5）——15+16=31 或 22+16=38，怎么都不是 17。
- 八项稿工作②还写“9 个未暴露 MCP 的 Atuohome 能力”：22−15=7≠9。一个数字写错，运行架构稿照抄。

**建议动作**：改正能力数表述，并核对“9 个未暴露能力”的真实数量。

## 五、真实空白（两稿都没覆盖）

### 问题 10：认证/登录完全缺失

**级别**：P2

**现状**：提纲 §9 #2 是高优先级待定（云形态倾向正式登录），但工作⑤的部署测试清单 9 条没有任何认证测试。销量/政策/TP 是商业敏感数据，无论云还是工位机都该有。

**建议动作**：至少补三条测试：未登录访问管理路由 → 401；readonly 用户 POST 上传 → 403；坏 xlsx → 报错拒绝，不入库不写半截数据（导入幂等）。

---

### 问题 11：langfuse 部署形态与数据合规

**级别**：P2

**现状**：
- 企业数据发 langfuse cloud 是否合规没讨论；self-host 又需要 Postgres + ClickHouse（违背砍基建基调）。
- 且评估跑批命令带 `--no-extensions`（提纲 §8.4），langfuse 扩展也被排除，“分数写回 trace”的链路在评估场景下是断的。

**建议动作**：合规没结论前敏感字段不送 cloud；明确“分数写回 trace”在评估场景下如何实现（或改为自建 Tracer 轨迹）。

---

### 问题 12：tokenizer 门禁用错对象

**级别**：P2

**现状**：工作⑦“上线前跑 tokenizer 回归（Qwen3 round-trip 80.1%）”——教材这个坑针对**本地部署模型**。Prism 主链路是 DeepSeek API（tokenizer 在服务端），本地只有 Qwen3-4B 做舆情离线打标且不在 agent loop 内。

**建议动作**：该门禁挂在舆情打标管线，挂在主链路是无效动作。

---

### 问题 13：次要项

**级别**：P2

1. **RAG 定位漂移**：提纲说是行业文档检索的 MinerU+FAISS 资产，运行架构稿描述成 review_tags 标签检索——两个“RAG”不是一回事。
2. **pi-subagents 定位**：提纲标注“⚠️ 示例级扩展非核心”，两稿当“✅已就绪”编排三维度并行。建议留串行 fallback。
3. **三维度并行成本**：并行是 3-4 倍 token 成本，与北极星的成本分母存在张力。建议提前定“并行相对串行的正确率增益门槛”。
4. **脱敏规则缺汽车字段**：14 类正则是通用 PII，汽车场景特有的 VIN 车架号（17 位固定格式）和车牌号不在规则集里，口碑原文里很常见。

## 收口顺序建议

1. **拍板部署形态**（云 vs 工位机）——决定砍基建清单、安全模型、认证方案。
2. **工作⓪ 加“数据可得性盘点”前置步**，确认 E5 三维数据真能凑齐。
3. **把 P0 挪到 ②TS 工具接线之前**，工作⓪ 立即开跑。
4. **做一次决策回写**：两份 HTML 里所有“已定调”条目回写提纲 §9/§4；已定调却还挂在待拍板列表的（舆情进主链路、口径分母）清掉；运行架构稿加版本标注。
5. **逐条裁决问题 5 的砍/建矛盾清单**，两处同步。
