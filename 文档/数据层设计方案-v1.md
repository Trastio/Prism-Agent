| # | 决策 | 否决的备选 | 理由 |
|---|------|-----------|------|

| D7 | 试水车系 = **银河 E5 + 零跑 B10** | 更大车系池 | 一老一新覆盖两种数据形态；E5 即提纲 §8.3 的金标准案例 |

## 1. 总体架构

```
autohome-agent（Python，数据生产者，长期保留）
  口碑采集 → owner_reviews（已有 15,750 条 / 36 车系）
  LLM 打标 → review_tags（已有 15,611 条）
  配置采集（新增）→ spec / item / config_value / item_map
  归一化层（物化为表）：spec_alias、item_map、（_normalize 词表迁库，二期）
                │
                ▼  同一 SQLite 文件（WAL，单写多读，跨进程安全）
                │
Prism-Agent（TS/pi + Web，数据消费者，只读）
  BI 模式：直读库/视图渲染图表（不经 harness）
  Agent 模式：语义工具读库（终局）/ MCP 桥（过渡）
  管理者导入：fact_terminal（CAM）、fact_policy（政策表）
  赋分层：score_default + score_override（Prism 侧新建，库里落地）
```

分界线画在**库**上：写入权全部在生产者（autohome 采集进程 + 管理者导入器），消费者一律只读。四张事实表共享同一版型身份层，口径同源的物理保证是 spec_id 精确 JOIN（见 §2）。

## 2. 版型身份层（棱镜的物理基础）

四个数据域、四套版型命名体系：

| 事实来源 | 键/命名 | 颗粒度 |
|---|---|---|
| 口碑（owner_reviews.spec_id） | 汽车之家原生 specid，填充率 99.9% | 按条 |
| 配置（之家配置页 valueitems[].specid） | 与口碑同体系（已核实混用安全） | 快照 |
| 销量+TP（CAM c1 车型编号） | 结构化编码 `制造商-年款-车型码-排量-变速箱-序号` | 半月→月 |
| 政策（政策表） | 车型+动力+版型名 三列拼接，无内部代码 | 月 |

### 表设计

```
dim_series (series_key PK, autohome_series_id, name, brand, level, energy_type)
dim_spec   (spec_key PK 内部代理键, series_key FK, autohome_spec_id UNIQUE,
            year, spec_name, first_seen, last_seen)
spec_alias (spec_key FK, alias, source)          -- CAM编号 / 政策表写法 / 之家别名
```

### 关键决策与理由

- **主锚 = 汽车之家 spec_id**：口碑与配置已同体系（唯一性已核实），身份层以它为 canonical，CAM 与政策表做 alias 挂靠。
- **CAM 的 c1 编号不能当业务键**：实测 18% 的编号跨时间片名称漂移（年款更名/编号复用），按 SCD 处理——身份层用内部代理键，c1+名称做快照（`dim_spec.cam_vehicle_id` + `spec_alias` 留存历史写法）。
- **按需映射，不做全量**：CAM 全市场 10,230 个版型，但只有核心车系池参与跨域交叉。试水 = E5（约 5 版型）+ B10（约 5-6 版型），共 ~12 行映射人工一次做完。池外 CAM 数据照样入库可查，不建映射。
- **政策表名称解析**：去前导空格/换行、统一年款词（“27款”）、动力串拆解（“1.5L-5MT”→排量+变速箱）。三层叫法不一致（目录↔sheet 名↔车型列）以**车型列**为准，目录仅作索引入口。

## 3. 口碑域：增量维护

### 3.1 现状诊断（2026-09-11 调研核实，行号引用基于当时工作区）

- 采集纯 lazy 触发（4 个入口），每次**全量翻页**（页大小 20、空页×3 熔断、年款补采兜底），无水位
- `review_id` 主键（`k_{Koubeiid}`），upsert 幂等 ✓；`fetched_at` 列已存在 ✓
- 标签只给零标签口碑打（collector.py:390-399），编辑后标签 stale（D3：接受为已知局限）
- 覆盖率分母三套口径（fetch_reviews: has_text/0.8；analysis: taggable/5% 拦截；前端 derive_status: 全量）——同类 bug，统一为一个函数
- task_status.json 只有 completed/failed、50 条逐出、运行态内存易失
- 活证据：fetched_at 最大 2026-07-24，库已 7 周未刷新

### 3.2 增量机制

```
collect_runs     (run_id, series_id, started_at, finished_at,
                  status,            -- validated / quarantined / failed
                  pages_fetched, reviews_seen, new_cnt, updated_cnt,
                  unchanged_cnt, rowcount_at_run, validation_note, error)
series_watermark (series_id PK, last_success_at, last_review_date,
                  api_rowcount_last, consecutive_failures)
```

- **stop-at-overlap**：口碑列表按时间倒序前提下，翻页至连续 2 页全命中已存在 review_id 且 post_date ≤ 水位即停。前置核查：实测列表排序；若不成立退回全量翻页（下游幂等不受影响，只是请求数多）。
- **staleness 门**（D2 的落地，位置仿 `_ensure_tags_ready`，工具层，不碰 agent-loop 红线）：查询入口发现水位 >14 天 → 触发增量。水位差数天 → 同步等（<30s）；差数月 → 返回旧数据 + 信封标注“数据截至 X，正在刷新”（数据真实性红线：如实披露）。
- **运行验证门**：new_cnt=0 且 rowcount 较水位降 >20%、空页率超阈、必填字段填充率 <95% → 本次 run 置 quarantined，**不推进水位**。
- **删除语义**：rowcount 下降/id 缺失 → 记 missing；连续 2 次有效运行确认 → `is_deleted=1`（tombstone，不物理删）。

### 3.3 保留的两个小加固（与重打无关的真 bug 修复）

1. `review_tags` 加 `UNIQUE(review_id, tag_name, sentiment)`（现在纯靠应用层去重，无 DB 兜底）
2. 覆盖率口径统一为单一函数（tagged / has_text），三处调用点收敛

### 3.4 明确不做（记录在案）

标签重打（D3）、content_hash 变更检测（随重打一起砍——没有消费者）、调度器（D2）、探索性 SQL 工具（§8）。

## 4. 配置域：快照管线

### 4.1 现状诊断

- config.py 实时调之家配置页（`config/series/{id}.html` 内嵌 var JSON），**零落库**，仅进程内缓存（900s/2h，重启即失）
- 数据自带分类分组（基本参数/车身/发动机/电动机/…），解析器现成（`get_series_info`/`_extract_var_json`/`get_full_config`）
- 反爬：字段名打碎在 span 中，靠代码常量表还原（autohome_api.py:427-512）——**还原 miss 必须告警**（之家改混淆方案的第一发现点）
- saleSpecs 只含在售 → 历史年款配置必须靠快照积累；**风险点：改款后老款能否再取到待实测（E5 试水核查点 ③）**

### 4.2 表设计（EAV + 归一化双存）

```
spec          (spec_id PK【同身份层】, series_key FK, year, name, msrp,
               status /*在售/停售=快照时点字段*/, first_seen, last_seen)
item          (item_id PK, category, normalized_key, display_name, value_type)
config_value  (spec_id, item_id, raw_value,           -- 保真可追溯
               num_value, unit, enum_value,           -- 归一化产物（数值/枚举）
               captured_at,  PRIMARY KEY(spec_id, item_id))
item_map      (raw_key, raw_category, item_id, transform, version)  -- 脏活物化为库资产
score_default (item_id, weight, rule, version)        -- 管理者唯一可改，版本化
score_override(user_id, item_id, weight)              -- 用户私有层
```

理由：配置项几百个且持续新增，宽表必死；EAV 的 diff/跨车型对比恰是其强项。raw 与 normalized 双存 = 数据真实性红线（可追溯）+ BI 可用（数值排序）的兼容。在售状态从“查询时实时拉取+600s 缓存”改为**快照时点字段**，口径可追溯。

### 4.3 四大查询形态验证（描述层不走 LLM 的物理基础）

版型阶梯（ORDER BY msrp）／两版型 diff（同 item JOIN 值不等）／跨车型对比（normalized_key JOIN + item_map）／加权赋分（JOIN 两张 score 表，SQL 确定性算术）——全为确定性 SQL，REST 层只做参数化封装，BI 工具直连同表。

### 4.4 采集

手动按需 CLI（D6）：拉车系配置页 → 复用现有解析器 → 过 item_map → upsert。年款切换前抢存老款为纪律。指导价（MSRP）在 spec 表；终端价/政策不进配置域（§5/§6）。

## 5. 销量与终端价格域（CAM 导入制）

### 5.1 源数据事实（2026-09-11 解剖）

- 主表 192,230 行 × 30 列，唯一键 (c1 编号, 年, 半月片)，0 合并单元格，机读友好
- 40 个半月片（2025-01中 ~ 2026-08末）；TP/优惠 91% 非空；零售数 47% 非空；‘-’ 占位混在数值列；“是否主销”空白=非主销（语义缺失≠空值）

### 5.2 表设计（D4：月度粒度）

```
fact_terminal (spec_key FK, period_month,          -- ‘YYYY-MM’
               msrp, tp, discount, retail_qty, mix,
               source='CAM', imported_at,
               PRIMARY KEY(spec_key, period_month))
```

聚合规则（导入时执行）：

| 字段 | 月度规则 |
|---|---|
| TP / 优惠幅度 | 两半月片均值 |
| MSRP | 月末片值 |
| 零售数 | 两片求和 |
| Mix | 按月零售数重算 |

清洗：‘-’→NULL；零售数缺失→NULL（分析层 COALESCE 0）；版型静态属性（级别/车身/排量…）不入库（源文件可查，避免与配置域重复维护）。

## 6. 政策域（B2B 渠道层）

### 6.1 源数据事实

136 sheets：封面/目录/4 张汇总表（含隐藏的“产品-分版型汇总表” 607×290 = 版型×42月×政策细项数值矩阵）/130 个车系明细（两代模板：A 宽表历史月份块拼接、B 窄表单月快照）。三种载体：明细数值矩阵、汇总富文本、变化点描述文本。质量坑：#REF! 坏列、月份块乱序重复、目录↔sheet 名三层不一致、版型名前导空格/车型名带换行、企业枚举脏值。

### 6.2 分级处理（核心设计）

| 载体 | 处理 | 落表 |
|---|---|---|
| 数值矩阵（隐藏汇总表 → 明细 sheet 二期） | ETL：月份块切割+块内 ffill | fact_policy |
| 汇总富文本 / 变化点文本 | **不硬结构化**，原文+元数据入库 | policy_text |

文本类留给 Agent 模式做检索+总结（“上月政策变了什么”→ agent 读 policy_text），数值分析走 fact_policy——**这是 data agent 与 ChatBI 的分界线在数据层的体现**。

### 6.3 表设计

```
fact_policy (spec_key FK, period_month,
             policy_type,          -- 年度商务/月度促销/金融个贷/置换(本品|非本品)/区域…
             sub_type, amount,     -- 元/台
             is_max_limit=1,       -- D5：额度上限语义标注
             condition_note,       -- “100%≤R＜110%” 等条件，保留原文
             source_sheet, imported_at,
             PRIMARY KEY(spec_key, period_month, policy_type, sub_type))
policy_text (period_month, brand, product, kind /*summary|change*/,
             text, imported_at)
```

### 6.4 口径与派生指标（D5）

政策 = 厂家对经销商的管理手段（渠道成本变量）；TP = 经销商与用户的成交价（消费层结果）。两表不互验、不加总。派生指标：

**政策传导率 = 终端优惠幅度 ÷ 政策合计上限**——高=经销商让利冲量（竞争激烈），低=渠道留存利润（车型强势）。分析链：厂家政策 → 经销商成本 → TP/优惠 → 版型销量，每环一张事实表，不跳步。

## 7. 跨域分析用例（试水即验证）

1. **E5 改款前后四角互证**（金标准用例）：口碑标签变化（改款前后）× 配置 diff × 版型销量结构（CAM）× 政策传导率——“舒适性是结构性短板”的完整证据链
2. **传导率对比**：E5 vs B10 的政策传导率时间序列——品牌渠道策略差异
3. **配置×销量**：版型销量结构 vs 配置阶梯（哪个配置组合真的走量）
4. **口碑×销量**：口碑的版型分布 vs 销量的版型分布（集中度错位=洞察）

四用例全部经 dim_spec 精确 JOIN 完成——身份层是棱镜理论的物理基础。

## 8. 桥接 Prism：harness engineering

### 8.1 过渡期（MVP）：MCP 桥

- `pi-mcp-adapter` 接 15 工具子集：fetch_reviews / get_review_analysis / get_dimension_reviews / get_trims / get_config / search_cars
- 信封层守卫（stop_answering/coverage）在工具内部，不受 MCP 转发影响
- **头号验证事项**：pi 扩展 `tool_call` 钩子能否拦截经 adapter 转发的调用——能拦才可用；不能则用 `tool_result` 钩子检信封兜底

### 8.2 终局：TS 语义工具直读库

- `better-sqlite3` 只读连接（readonly），WAL 下与生产者写入无冲突（现网双进程读写已验证该模式）
- 只做 **Operational 工具**（参数化+枚举输入+prepared SQL；行业共识：探索性工具不进生产，其终局是收敛为运营性工具）
- 口径一致两个物理保证：**spec_id 精确 JOIN**（替掉现 `spec_name LIKE` 模糊匹配）；**维度映射物化 SQL 视图**（`_map_to_business_dim` 下沉，BI 与 Agent 读同一视图）
- 护栏双层：工具内信封（coverage+as_of）+ pi 扩展 `tool_call` fail-closed；`context` 钩子每轮注入数据水印

### 8.3 新鲜度一等公民

每个语义工具返回 `as_of`（取自 series_watermark）+ coverage；工具描述软约束“回答必须披露数据截止时间”；评估体系（提纲 §8）确定性断言含新鲜度检查（问“最近一个月”时答案必须基于真实 as_of）。

## 9. 实施顺序

| 阶段 | 内容 | 落点/纪律 |
|---|---|---|
| Phase 0 | series_watermark+collect_runs、stop-at-overlap、staleness 门、review_tags UNIQUE、覆盖率口径统一、CLI 刷新脚本 | autohome 仓库，走 OpenSpec；全在工具/采集层，不碰 loop.py/chat_routes.py 红线 |
| Phase 1 | 身份层 12 行映射 → CAM 月度导入器 + fact_terminal → 政策隐藏表 ETL + fact_policy/policy_text → 配置快照采集 → 第一个 TS 语义工具（或 MCP 桥验证） | Prism-Agent 仓库 + autohome 侧导入器 |
| 试水核查 | ① E5/B10 身份映射 ② 两车系口碑是否已采集 ③ E5 改款历史配置可得性 ④ CAM 导入清洗验证 ⑤ 政策两代模板各踩一种 | 每步出验证记录 |
| Phase 2 | BI 视图层、双模式对账（口径一致回归）、政策明细 sheet ETL、车系池扩容 | 按试水结论定 |

### 待定项（本文档产生的新待定）

- 核心车系池规模（试水双车系跑通后定）
- E5 历史配置可得性（试水核查点 ③，取不到则改款对比的配置维度需用户手工补录）
- staleness 阈值（暂定 14 天，按真实查询体验调）
